A platform: five services, and everything that watches and administers them

One diagram with every cross-cutting case at once: logs and traces pushed by every service, metrics pulled from every service, secrets pushed to most, a shared event bus, dashboards and alerting behind them, and an admin path through a bastion with a different protocol for each target. Drawn here first as Trace draws it today (plain links, no layout help), then as I would draw it by hand.

1. Today, plain links

Forty-odd links, and the layout cannot tell the story from the cross-cutting ones: every service is tied to Loki, Tempo, Prometheus and Vault, so the services, the stores and the observability stack are pulled into a tangle. The merged-links pass bundles some of them, which helps little once the layout has placed everything around them.

2. How I would draw it

The reading order. The runtime story is the top: users, gateway, the five services in their cluster. Everything the services share hangs beneath them as a ladder: one horizontal line per concern, each with a tint and its hub at one end. Hubs that give (Vault, Prometheus) are on the left and the services receive with an arrowhead; hubs that collect (Loki, Tempo) are on the right and the lines end in an arrowhead at them. Each service drops one stub to each line it uses: a column of dots per service, so "who uses what" reads as a matrix (Catalog has no secrets: its column skips that line).

Everything else stays an ordinary diagram. Dashboards and alerting are plain links from the hubs; admin is a small zone at the top left, and the bastion's three targets are three dashed links, each with its own protocol, so they are not bundled. A link crosses a bus with a small hop, never a gap.

4. The DSL that follows

The same two ideas as before, and nothing else: bus is a node drawn as a line that spans what it serves, and a & b & c is shorthand for several links. The ladder is a column block holding the services row and one row per rung; a rung is a row holding the hub and the bus.

column {
  row "services" {
    orders [package]: Orders
    catalog [list]: Catalog
    payments [credit-card]: Payments
    accounts [user]: Accounts
    notify [bell]: Notifications
  }
  bus events:  events | Kafka :9092
  row { vault [lock]: Vault        bus secrets: secrets | agent injector }
  row { prom [activity]: Prometheus bus metrics: scrape /metrics :9100 }
  row { bus logs: logs | Fluent Bit       loki [file-text]: Loki }
  row { bus traces: traces | OTLP :4317   tempo [route]: Tempo }
}

Reading it: the services row is where it has always been; each bus line is a node in a row under it; a hub that gives is written before its bus (row { vault ... bus secrets ... }), one that collects after. The direction of the arrowheads comes from the links (vault -> secrets -> orders & ...): the first link ends at the bus with no arrowhead, the last carries it. A bus with no hub (events) uses <->.

5. Where this stresses the idea

  • The stubs cross. Each service has five stubs and each stub crosses the rungs above its own (hops). This is the price of the matrix, and why the rungs should be ordered with the busiest line nearest the services. With more than about six concerns it would need a second ladder on top.
  • The ladder must sit under a row of services. A column of services wants vertical buses beside it, which then cross the links to the gateway and the data stores.
  • Hubs at the ends of rungs need the rung to be as wide as the services row plus the hub: the span rule has to include a node that is not a stack member.
  • Data stores are not drawn here. Put one per service in its note (Orders | Postgres); a shared one is one more rung.
